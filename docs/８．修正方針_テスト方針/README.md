# 修正記録の運用ルール

## 目的と責務

このディレクトリは、既存実装をなぜ、どのような方針で変更し、実際に何を確認したかという変更履歴（History）を保存する。

`docs/１．設計書/`は現在の正式仕様（Current State）の正本であり、修正方針・修正結果は設計書の代替にしない。挙動を変更した場合は、現在仕様を適切な設計書へ反映し、変更の背景と経緯をこのディレクトリへ記録する。

## 対象

原則として、実装変更、挙動変更、UI変更、Rule変更、Architecture変更、Phase Follow-up、Regression fix、複数ファイルに影響する修正など、後から変更理由を追跡する価値がある修正を記録する。単純な誤字や同等の微小修正は、既存運用との整合を確認したうえで記録を省略できる。

## 作業手順

既存実装に対する修正・Follow-upは、原則として次の順で進める。

1. 修正対象を確認する。
2. 同じ修正単位の`修正方針.md`を作成する。
3. 実装する。
4. テストする。
5. 必要に応じて正式設計書を更新する。
6. 同じ修正単位の`修正結果.md`を作成する。
7. `修正記録一覧.md`へ方針・結果の対応を追加する。
8. commitする。

## 各文書の役割

- `○○_修正方針.md`: これから何を、なぜ、どの範囲で、どのように直すかを実装前に記録する。
- `○○_修正結果.md`: 実際に変更した内容、テスト結果、未確認事項、残課題を実装・テスト後に記録する。
- `修正記録一覧.md`: 修正単位ごとに方針と結果を追跡する索引とする。

方針と結果には共通の修正単位が分かるファイル名を使用し、一覧から両方へ相対リンクする。過去記録の不足を推測で補完したり、既存ファイルを一括renameしたりしない。
