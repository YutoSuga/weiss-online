- Costは全件事前検証し、記載順の同期支払い中にRule Checkを挟まない。AUTOは`costIndex / costPaymentInProgress`を保持し、全支払い後に次stepを保存してCheck Pointへ進む。ACTは同期的`payCosts()`で同じ境界を実現する。
- `resolveCheckPoint()`はRule Checkを先に解決する。Refresh後のPenaltyは独立候補で、Level Up等との順序選択が可能。stack全体にACT/AUTOがあれば新Pending提示を抑止し、Rule child完了後に親Abilityへresumeする。Ability自身のCOMPLETE/pop後にTurn / Non-Turn順のCheck Timingへ戻る。

## 4. Renderer / Pending AUTO（分類D）

### 現行の判定箇所

- `client/js/core/renderer.js:87`の`renderPendingAutoSelection(gameState)`が表示を担当する。
- この関数自身が対象PlayerのPendingを抽出し、全collectionからsource Cardを探し、PRINTED/RULE能力を解決する。`getCostsDisabledReason()`と`getEffectsDisabledReason()`を呼び、RULE sourceでは`card.zone === WAITING_ROOM`を判定してdisabled理由を作る。判定結果を受け取って表示するだけではなく、表示層がドメイン判定を行っている。
- Engineの`getPendingAutoOptions()`も候補抽出・能力解決・`#getPendingAutoDisabledReason()`を行うが、RendererとPendingAutoControllerはこのQueryを利用していない。現行参照は主にテストである。
- Engineの標準アンコール判定は`STANDARD_ENCORE_3`だけを対象に、`locateCard()`のcollection所在とmaster player一致を確認する。RendererはRULE全般へCard metadataのzoneだけを確認する。判定順もEngineは所在→Cost→Effect、RendererはCost→Effectの後にRULE所在理由を上書きするため、完全に同じ契約ではない。
- PendingAutoCollectionは設計上の単一Collectionで、実装は`gameState.ruleState.pendingAutos`配列である。独立したavailability判定クラスはない。GameEventDispatcherとTrigger Detectorは誘発事実を生成し、Cost/Effect可否で生成を抑止しない。

### 表示・選択・commit

| 時点 | 再検証経路 |
| --- | --- |
| 描画 | Rendererが独自にCost / Effect・RULE対象を再評価 |
| Query | Engineの`getPendingAutoOptions()`が共通disabled理由を返す（現在の画面経路では未使用） |
| 使用選択 | `selectPendingAuto()`がPending所属・能力・共通disabled理由を検証 |
| commit直前 | `#commitPendingAuto()`が共通disabled理由とPrepared Costを再検証し、Pending consume / AUTO push |
| 支払い直前 | `executeAutoAbilityProcess()`がPrepared Costを再検証してからmutation |

`phaseF5C`のCost状態変化・部分支払い防止、`phaseF5D1`のアンコール所在、`phaseF5D2`の相手Stock有無とUI構造を確認した。ただしUIテストにはソース文字列検査があり、RendererとEngineの全理由一致を動作として保証するテストではない。今回ブラウザを操作していない。

### 次の推奨

1. 既存Queryの利用とavailability判定の単一経路化を先に設計し、Engine / ドメイン側の責務とする。
2. Rendererはカード表示、使用可否と理由の表示に限定し、ControllerはID・選択入力をEngineへ渡す。collection / Card metadataのどちらを正とするかも一貫させる。
3. 表示用Queryとcommit直前の検証は同じ評価契約を使い、現在Stateで再評価する。Pendingに可否を固定保存しない。
4. Cost NG / Effect NG / source所在変化、使用しない、Prepared Costから戻る、親Ability resumeと提示タイミングの回帰を維持する。
5. その境界が整ってからCondition評価とCONDITION / COST / EFFECTの理由区分を追加する。

現状でEngineだけにConditionを追加すれば表示とcommitが食い違い、Rendererにも追加すれば責務違反・重複が増える。したがってCondition実装より先に整理する。今回はResolver新設、API変更、リファクタリングを実施していない。

## 5. Condition・Loaderの確認

- `CardAbility`はimmutableな`conditions[]`を保持するが、汎用Condition Resolver / Handler、正式Condition Type、Condition availabilityの評価はない。
- LoaderはACTで非空配列をrejectし、runtimeのACT検証も拒否する。AUTOはactivationTrigger / activeZonesとCost / Effect schemaを検証する一方、Condition Type / 非空配列を同様にはrejectしない。
- メモリ上だけに未対応Conditionを持つAUTOを作った診断で、Loader / Registry生成成功、Pending 1件生成、`disabledReason: null`、commit成功を確認した。同じ非空ConditionをACTへ変更するとLoaderで拒否された。repositoryのデータ・テストファイルは変更していない。
- 現在の正式実行データのconditionsは空であり、既存の105テスト成功はこの負債がないことを意味しない。Effect Group内部の結果比較は実装済みだが、`CardAbility.conditions[]`の汎用評価とは異なる。
- 正本が既に記録する「導入前はAUTO非空Conditionをfail-fast、導入時は対応Typeだけallow-list、未対応Type reject」の方針を維持する。実装は別タスクで行う。
