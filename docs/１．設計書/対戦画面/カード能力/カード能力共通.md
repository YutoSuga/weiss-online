# カード能力共通設計

## 1. 目的と正本の境界

本書は`CONTINUOUS / AUTO / ACT`を問わず、カード能力の定義と実行基盤に共通する仕様の正本である。Ability Type固有の発動・候補選択・実行フローは[ACT能力共通](起動効果/ACT能力共通.md)と[AUTO能力共通](自動効果/AUTO能力共通.md)を正本とする。

| 責務 | 正本 |
| --- | --- |
| CardAbility schema、Cost / Condition / Effect、Ability ProcessとRule Processの接続 | 本書 |
| ACTのタイミング、Query、`ACT_ABILITY`、集中 | [ACT能力共通](起動効果/ACT能力共通.md) |
| Game Event、Trigger Detection、Pending AUTO、Check Timing、`AUTO_ABILITY` | [AUTO能力共通](自動効果/AUTO能力共通.md) |
| Process stack自体のAPIと不変条件 | [Process設計](../../システム共通/プロセス.md) |
| Refresh / Refresh penalty / Level Upの検出と解決 | [Rule Check設計](../../システム共通/ルールチェック.md) |
| 複合Cost + 山札検索AUTOの具体例 | [複合コスト・山札検索AUTO](自動効果/処理パターン/複合コスト・山札検索AUTO.md) |

公式ルールの採用版は **ヴァイスシュヴァルツ総合ルール ver.1.112（2026-08-24更新）** である。本書はルール処理を再定義せず、[リポジトリ内のルール参照メモ](../../../ルール参照/ヴァイスシュヴァルツ総合ルール_ver1.112.md)と上記設計の接続境界だけを扱う。

## 2. CardAbility共通schema

`CardAbility`はCardMaster内に保持する不変の構造化データである。実行時に別のglobal IDは作らず、`Card.instanceId + CardAbility.id`で定義を特定する。詳細なCardMasterとCard instanceの境界は[カードデータモデル](../../システム共通/カードデータモデル.md)を参照する。

```js
CardAbility {
  id, type, keywords, text,
  activationTrigger, activeZones,
  conditions, costs, effects
}
```

| field | 共通契約 / 固有性 |
| --- | --- |
| `id` | 同一CardMaster内で能力を識別する非空文字列 |
| `type` | `CONTINUOUS / AUTO / ACT`のいずれか |
| `keywords[]` | Ability Typeとは別のkeyword。現行の実行対応はACTの`BRAINSTORM` |
| `text` | 表示原文。Engineはこれを解析しない |
| `activationTrigger` | 主にAUTOが使う誘発契機。ACTの共通プレイタイミングではない |
| `activeZones[]` | 主にAUTOの候補列挙でsourceが有効なZone |
| `conditions[]` | Cost / Effectからは導出できない、能力固有の必要状態・条件 |
| `costs[]` | Costをテキストの記載順に保持 |
| `effects[]` | Effectを解決順に保持 |

モデルは全fieldをJSON互換値としてdeep clone / freezeする。ただしschemaを保持できることと、Engineが実行できることは別である。AUTOのTrigger schemaやACTの実行条件は各Ability Type文書で定める。CONTINUOUSの評価基盤は未実装である。

## 3. Cost共通設計

### 3.1 Resolver / Handlerと対応Type

`costResolver.js`はTypeからHandlerを取得し、schema検証`validate`、非mutationの支払可能性判定`getDisabledReason`、mutationの`pay`を分離する。現行対応Typeは次の**3種だけ**である。

| Cost Type | Parameters | 動作 |
| --- | --- | --- |
| `PAY_STOCK` | `amount: positive integer` | 自分のStock top（配列末尾）から指定枚数をWaiting Room topへ移動 |
| `MOVE_DECK_TOP_TO_CLOCK` | `amount: 1`固定 | 自分のDeck topを1枚Clockへ移動 |
| `REST_SELF` | なし | source自身をSTANDからRESTへ変更 |

`prepareCostSelections()`と`getPreparedCostsDisabledReason()`はACT/AUTO共通の将来拡張境界である。現行3TypeはEngineが対象を一意に決定するため、ユーザー選択を要求しない。

### 3.2 複数Costとpayment boundary

1. 使用可否判定とmutation直前に、全Costを現在Stateで検証する。
2. 1件でも不可なら、1枚も移動・RESTしない。
3. 可能なら`costs[]`の記載順に同期的に支払う。
4. Cost item間でRule Check / Check Timingを起動しない。全Costの支払が1つのpayment boundaryである。
5. 全件完了後に次stepを保存し、Cost後Check Pointへ入る。

`costIndex`は完了済み数、AUTOの`costPaymentInProgress`は不可分境界の監査値である。ACTは`payCosts()`の同期完了性で同じ境界を実現しているが、現行contextに`costPaymentInProgress`は持たない。

### 3.3 Cost Type追加規則

データだけを先行登録せず、定数、Handler、Loader/runtime validation、支払可否・記載順・Check Pointのtest、本書の一覧を同時に追加する。選択対象がある場合は、選択中はmutationせずPrepared Costとして保持し、commit直前に再検証する。未知TypeはLoaderまたはruntime Resolverでfail-fastし、無視しない。

## 4. Condition / Effect共通設計

### 4.1 Condition

`conditions[]`は、**Cost / Effectからは導出できない、能力固有の必要状態を宣言する**共通schemaである。例は「このカードが前列にいる」、sourceが特定Zone / カード状態にある、または能力固有のゲーム状態を満たすことである。次の三者を混同しない。

| 区分 | 責務 | `conditions[]`に入れない例 |
| --- | --- | --- |
| Condition | Cost / Effectと独立した能力固有の必要状態 | — |
| Cost availability | 記載Costを現在Stateで支払えるか | `PAY_STOCK 3`のStock枚数、手札Costの対象有無 |
| Effect availability | Effectの開始に必要な対象・処理対象があるか | 検索対象、相手Stock topなどEffect対象の有無 |

使用可否は概念上、`Condition ∧ Cost availability ∧ Effect availability`として統合し、各結果と理由の区分を保つ。これによりUIは単なるbooleanだけでなく、将来`CONDITION / COST / EFFECT`のどのavailabilityがNGかを提示できる。各Cost / Effect Handlerの`getDisabledReason`は後二者の現行実装であり、Conditionの代用ではない。

Conditionは`activationTrigger`とも分離する。Triggerは「どのEventで誘発したか」、Conditionは「使用可否判定時のStateが能力固有の必要状態か」を表す。Condition NGはTrigger不成立と同義ではない。AUTOではTrigger成立時にPendingを生成した後、Check Timingの使用可否判定でConditionを現在Stateから評価する。

現行は汎用Condition Resolver / Handlerも正式対応Condition Typeもない。ACTはLoaderと実行時の両方で空配列だけを受理する。AUTOもLoaderで非空配列・配列以外をfail-fastする。未指定は空配列として扱う。Loaderを経由しない非空ConditionもEngineの使用可否評価で使用不可とし、silent ignoreを防ぐ。汎用Condition評価は未実装であり、非空Conditionを実行可能データとして追加してはならない。Condition Typeは実装対象カードを決めたときに必要最小限から導入し、`SELF_IS_REST`等を実カード調査より先に大量定義しない。Type追加時はschema、Resolver / Handler、Loader/runtime validation、各Ability Typeの評価時点、理由区分、testを同時に追加する。

### 4.2 Effect Resolver / Handlerと対応Type

`effectResolver.js`はEffect schema、Effect IDの一意性、結果参照、使用可否、単純Effectの`resolve`を共通化する。一方、入力待ちや小刻みのresumeを要するEffectの実行制御は現行`GameEngine`のACT/AUTO経路に残る。「すべてがHandlerで実行される」とはみなさない。

| Effect Type | 位置付け |
| --- | --- |
| `TEST_LOG` | 開発/テスト専用 |
| `BRAINSTORM_REVEAL` | ACT集中固有のReveal / Resolution処理 |
| `EFFECT_GROUP` | Effect結果の数値が`min`以上なら子Effect列を実行 |
| `SEARCH_DECK` | 共通の山札検索child Process |
| `ADD_TO_HAND` | `EFFECT_RESULT`のinstance IDをHandへ移動 |
| `SHUFFLE_DECK` | Deckをshuffle |
| `ENCORE_RETURN` | RULE AUTO（標準3コストアンコール）固有 |
| `REPLACE_OPPONENT_STOCK_TOP` | AUTO①の相手Stock置換 |

Effectは基本的に1件解決するたび、次の`effectIndex`とstepを先に保存してCheck Pointへ入る。`Effect.id`はAbility-localで一意な結果識別子、`effectIndex`は進行位置である。`effectResults[effectId]`へCard objectではなくinstance IDや数値を保存し、`{ source: "EFFECT_RESULT", effectId, field }`だけを明示参照として解決する。

Effect Type追加時もCostと同様に、定数、Handlerのschema/availability/executionのうち必要な責務、Ability Processとchild Processの接続、Loader/runtime validation、test、本書を同時更新する。

## 5. Ability Process / Rule Check共通原則

### 5.1 Process contextとstack

Abilityの実行は`ACT_ABILITY`または`AUTO_ABILITY` Processで表す。Processは`type / playerId / step / status / context`を持ち、contextにsource/abilityの識別子、`costIndex`、`effectIndex`、`effectResults`等の作業メモリを保持する。Card objectやGame State全体を複製しない。

Abilityを親、`SEARCH_DECK`やRule Processを子としてstackへpushする。子のpop後は、親が先に保存したstep/indexからresumeする。これがCost / Effectの二重実行を防ぐ。ACT/AUTOでstep定数や固有contextは共用せず、このstack不変条件だけを共通とする。

### 5.2 Check Pointとinterrupt / resume

```text
Cost全件完了 → 次step保存 → Check Point
Effect 1解決 → index/次step保存 → Check Point
Ability COMPLETE → pop → 最終Check Point / 通常Check Timing
```

`resolveCheckPoint()`は`resolveRuleCheck()`の入口であり、Refresh / Refresh penalty / Level Upの候補があればRule ProcessがAbilityの上へ割り込む。Rule Processの詳細は本書で定義しない。Rule状態が安定したら保存位置から親Abilityへresumeする。

特に、Process stackのどの深さにも`ACT_ABILITY / AUTO_ABILITY`が残る間はAbility解決中である。その間に生成されたPending AUTOはcollectionに保持するが、Ruleが安定しただけでは提示せず、親Abilityをresumeする。Abilityが`COMPLETE`となりpopされた後に初めて通常Check Timingへ進む。

```text
Rule Process完了 ≠ Ability完了
Pending生成/保持 ≠ PendingのUI提示/AUTO開始
```

## 6. ACT集中と複合Cost AUTOの分担

| 共通基盤 | ACT集中固有 | AUTO固有 |
| --- | --- | --- |
| Cost Handler / `payCosts()` | `BRAINSTORM_REVEAL` | Game Event / Trigger Detection |
| Cost後・Effect後Check Point | Resolution領域とReveal確認 | Pending AUTOの生成・使用/不使用 |
| Rule Checkへの接続 | CX枚数と`EFFECT_GROUP` | `AUTO_ABILITY`への移管 |
| Process stack / interrupt / resume | `ACT_ABILITY_STEP`とMAINへの復帰 | `masterPlayerId`とCheck Timingの優先順 |
| `SEARCH_DECK` / `CardSelectionView` | 集中の検索条件 | AUTO②のLv条件付き0～1枚検索 |

## 7. 更新先の判断基準

- 新しいCost / Condition / Effect TypeとAbility Process共通不変条件は本書。
- ACTの使用可能性、step、UI、keywordはACT文書またはそのkeyword文書。
- AUTOのTrigger、Pending、同時AUTO、Check Timing、UIはAUTO文書。
- 特定の複合フローは処理パターン文書とし、共通契約を再定義せず本書へリンクする。
- 個別カードは汎用Trigger / Condition / Cost / Effectの組み合わせとし、カードID分岐を共通基盤へ追加しない。

## 8. 現行実装との差異・残課題

- 基本ガードは実装済みである。AUTOの非空`conditions[]`はLoaderでfail-fastし、runtimeでも使用不可にする。Condition基盤導入時は対応Typeのallow-list検証へ置き換え、未対応Typeを明示rejectする。
- Effect Resolverはvalidationと一部の単純Effect executionを共通化しているが、入力待ち・child Processを持つEffect executionはACT/AUTOのGameEngine分岐に残る。新Type追加時に重複が生じる場合は、共通HandlerとAbility固有orchestratorの境界を再評価する。
- CONTINUOUSはschema上のAbility Typeだけが存在し、評価Process / Condition基盤は未実装である。実装時は本書の共通契約を使い、ACT/AUTO固有フローを流用しない。
