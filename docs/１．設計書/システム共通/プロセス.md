# Common Process Foundation v1

## Purpose

共通プロセス基盤は、REFRESHやLEVEL_UP、能力解決などによる処理の中断・再開のため、現在の実行位置を管理する。

- GameEngineは「何を実行するか」を決定する。
- ProcessManagerは「現在どのProcessを実行中か」を管理する。
- Rendererは表示だけを担当する。
- Controllerはユーザー入力だけを担当する。

ProcessManagerは、割り込み条件、優先順位、ゲームルールを判断しない。

## ruleState

GameStateは次の状態を持つ。

```js
ruleState = {
  processStack: [],
  pendingInterrupts: [],
  pendingChecks: [],
  pendingAutos: [],
  nextGameEventSequence: 1,
  nextPendingAutoSequence: 1,
};
```

- `processStack`: 実行中および割り込みによって中断されたProcess。末尾が現在Process。
- `pendingInterrupts`: 複数の実行可能Rule候補をプレイヤーが選ぶための待機列。
- `pendingChecks`: Refresh完了時に登録されるRefresh Penalty等のルール処理待機列。
- `pendingAutos`: Eventで誘発したAUTOの単一Collection。Rule待機列へ混ぜない。
- `nextGameEventSequence` / `nextPendingAutoSequence`: Event / PendingのID採番。

各GameStateは独立した配列を生成し、他のGameStateと共有しない。

## Process structure

```js
{
  type,
  playerId,
  step,
  status,
  context,
}
```

- `type`: `PROCESS_TYPE`で定義したプロセス種別。
- `playerId`: 対象または現在のプレイヤー。
- `step`: **次に実行する処理**。完了済みの処理ではない。
- `status`: `running`または`waiting_input`。
- `context`: プロセス固有のデータ。

`PAUSED`状態は持たない。`processStack`の最上段より下にあるProcessは、スタック位置によって暗黙的に中断中と判断する。

## ProcessManager

`ProcessManager`は`GameState`を受け取り、`gameState.ruleState.processStack`を直接管理する。GameStateから分離した非公開スタックは持たない。

- `pushProcess(process)`: 検証・浅いコピー後、Processを末尾へ追加する。
- `popProcess()`: 現在Processを取り除いて返す。空の場合は`null`。
- `getCurrentProcess()`: 現在Processを返す。空の場合は`null`。
- `updateStep(step)`: 現在Processの次の処理を更新する。空の場合は`null`。
- `updateStatus(status)`: 現在Processの状態を更新する。空の場合は`null`。

## REFRESH Process v1

REFRESHはRule Checkによる自動検出またはGameEngineの明示呼び出しで開始し、ProcessManagerを通して次のProcessを`processStack`末尾へ追加する。

```js
{
  type: PROCESS_TYPE.REFRESH,
  playerId,
  step: REFRESH_STEP.MOVE_WAITING_ROOM_TO_DECK,
  status: PROCESS_STATUS.RUNNING,
  context: {},
}
```

`REFRESH_STEP`は次の順で進む。stepは常に「次に実行する処理」を表す。

```text
MOVE_WAITING_ROOM_TO_DECK
    ↓ 控え室の全カードを山札へ移動
step = SHUFFLE_DECK
    ↓ render
SHUFFLE_DECK
    ↓ 既存のDeck.shuffle()を実行
step = COMPLETE
    ↓ render
COMPLETE
    ↓ pendingChecksへRefresh Penaltyを登録
    ↓ processStackからREFRESHをpop・再チェック
```

REFRESHのstatusは全stepで`PROCESS_STATUS.RUNNING`とする。Phase E以降、完了時は`completeCurrentProcess()`を通り、pop後に`resolveCheckPoint()`でRule処理を再判定し、安定時だけPending AUTO提示を検討する。結果がCONTINUEなら、下にある既知Processを保存済みstepから再開する。

控え室が空でもREFRESHは拒否せず、移動枚数0枚の安全なno-opとしてシャッフルと完了まで実行する。これは開発用の明示実行を安全にするためであり、敗北条件を意味しない。

Phase B導入時に対象外だったもの（現在はRule Checkから接続済み）：

- 山札切れによるREFRESHの自動検出
- REFRESHの実行可能条件判定
- リフレッシュペナルティおよび`pendingChecks`
- `pendingInterrupts`
- 敗北条件

## LEVEL_UP Process v1

LEVEL_UPはRule Checkによる自動検出またはGameEngineの明示呼び出しで開始し、次のProcessをProcessManager経由でpushする。

```js
{
  type: PROCESS_TYPE.LEVEL_UP,
  playerId,
  step: LEVEL_UP_STEP.PREPARE_SELECTION,
  status: PROCESS_STATUS.RUNNING,
  context: {},
}
```

stepは次の順で進む。

```text
PREPARE_SELECTION (running)
    ↓ clock[0]からclock[6]の存在を検証
WAIT_FOR_SELECTION (waiting_input)
    ↓ LevelUpControllerから選択を受け取る
RESOLVE_SELECTION (running)
    ↓ 選択カードをレベル、残り6枚を控え室へ移動
COMPLETE (running)
    ↓ LEVEL_UPをpop
```

候補は常に現在のGameStateの`clock[0..6]`から導出し、Process contextへカード、カードID、候補配列を複製しない。contextは開始時に空で、入力確定後に`selectedClockIndex`だけを保持する。選択解決時にもクロック状態とインデックスを再検証する。

`WAIT_FOR_SELECTION`中は通常フェイズ進行とCLOCK操作を停止し、LevelUpControllerだけが入力を受け付ける。Phase E以降、完了時は`completeCurrentProcess()`を通ってpop・`resolveCheckPoint()`を行い、CONTINUEなら下にある既知Processを保存済みstepから再開する。

Phase C導入時に対象外だったもの（現在はRule Checkから接続済み）：

- `clock.length >= 7`によるLEVEL_UPの自動検出
- REFRESHとLEVEL_UPの同時割り込み順序
- `pendingInterrupts` / `pendingChecks`の解決
- リフレッシュペナルティ
- 敗北条件

## SEARCH_DECK Process（F-4B）

`MAIN_PHASE → ACT_ABILITY → SEARCH_DECK`または`AUTO_ABILITY → SEARCH_DECK`の子Processとして、`PREPARE → WAIT_FOR_SELECTION → COMPLETE`を持つ。contextにはplayerId、sourceCardInstanceId、abilityId、effectId、min/max、filter、selectedCardInstanceIdsを保持する。入力確定後に親ACT / AUTOのeffectResultsへinstanceId配列を保存し、Effect位置を更新してpop/resumeする。BRAINSTORM_REVEALの山札切れは同じACTを残したまま既存REFRESH / REFRESH_PENALTYを積み、保存済み移動数から再開する。
# BRAINSTORM_REVEALの入力待ち（Phase F-4B UI/UX Follow-up）

Reveal対象が揃ったACTは`WAIT_FOR_BRAINSTORM_CONFIRMATION / WAITING_INPUT`となる。Process contextの`movedCardInstanceIds`をReveal順の正本とし、ControllerやRendererに進行状態を持たせない。「控え室に置く」の入力後、対象instanceだけを移動し、ACTのEffect進行位置を更新して`CHECK_POINT_AFTER_EFFECT`から再開する。Reveal途中のREFRESH / REFRESH_PENALTY割り込みは従来どおり保存済みcontextから再開する。

## Phase F-5B: Game EventとProcessの境界

Game EventはProcessではない。Engineの意味的なmutationが全て完了した直後に1回だけ発行し、同期的なTrigger DetectionとPending AUTO生成までを行う。DetectorはProcessをpushせず、Cost / Effect / render / Rule Checkを実行しない。

```text
Game State mutation完了
  → Game Event確定
  → PRINTED / RULE候補取得
  → activationTrigger照合
  → gameState.ruleState.pendingAutosへappend
  → F-5B終了
```

`pendingChecks`はRefresh Penalty等のRule Check専用、`pendingInterrupts`はRule Process選択専用、`pendingAutos`はAUTOがEventによって誘発した事実専用であり、相互に流用しない。F-5Bでは既存`resolveRuleCheck()`とProcessのinterrupt / resumeを変更しない。

F-5Cでは`resolveCheckPoint()`を正式導入し、(1) Rule Checkを反復して安定化、(2) Turn PlayerのPending AUTO、(3) Non-Turn PlayerのPending AUTO、の順にProcessを開始する。F-5BのPending生成自体はphase、`MAIN_PHASE`、`WAITING_INPUT`に依存しない。

## Phase F-5C Pending AUTO / Check Timing

通常ProcessのCheck Pointは`resolveCheckPoint()`を入口とする。ACT / AUTOがstackのどこかに残っている間は、Rule Checkを行っても新たなPending AUTOを提示しない。Rule child完了後は親Abilityを保存済み位置から再開し、Ability自身の完了後に通常Check Timingへ戻る。複数Costの全支払い後にのみCheck Pointへ入る境界は[カード能力共通](../対戦画面/カード能力/カード能力共通.md)を正本とする。

内部で既存`resolveRuleCheck()`を先に実行し、安定後に単一`pendingAutos`からTurn Player、次にNon-Turn Playerを`masterPlayerId`で抽出する。`PENDING_AUTO / WAITING_INPUT`は1件でも選択を要求し、ID指定なのでcollectionの生成順は解決順ではない。

`PENDING_AUTO`は`SELECT_AUTO → SELECT_COST（必要時のみ）`を担当し、Prepared CostはGameStateを変更しない。「効果選択に戻る」はPrepared値だけを破棄する。最終再検証後、Pendingをconsumeして`AUTO_ABILITY`をpushした時点が不可逆境界であり、以降は`PAY_COST → RESOLVE_EFFECT → COMPLETE`となる。AUTO中のEventは新Pendingを追加するが、現在AUTOへ割り込まず、COMPLETE後の`resolveCheckPoint()`で全候補を再評価する。

## SELECT_ZONE_CARD Process（F-5D-2）

AUTO①の公開領域選択は`AUTO_ABILITY → SELECT_ZONE_CARD`子Processとして`WAIT_FOR_SELECTION / WAITING_INPUT`を持つ。contextは対象Player、source/destination Zone、min/max、選択instance IDを保持し、候補カード配列は現在Stateから導出する。確定時にexactly 1枚を再検証して通常移動し、pop後は親AUTOを保存済みEffect indexから再開する。表示はSEARCH_DECKと`CardSelectionView`/モーダルを共有するが、山札検索やshuffleの意味は持たない。

## PHASE_TRANSITION Process：Phase AUTO / resume

Phase進行の継続を`ruleState.processStack`へ保持する。`context { fromPhase, toPhase }`、現在ターンの`playerId`、`RUNNING`を持ち、次stepを保存して既存Check Timing coordinatorへ渡す。終了入力の確定は前Phaseの終了事実であり、終了AUTOを扱う間は`gameState.phase`を前Phaseに保持する。

```text
MAIN / CLOCK COMPLETE、またはnextPhase / enterPhase
  ↓ Phase固有Processを引き継ぎ、PHASE_TRANSITIONをpush
END_PHASE：終了確定済み → PHASE_ENDED（異なるPhaseのときだけ）
  ↓
CHECK_POINT_AFTER_END：次stepをENTER_PHASEへ保存
  ↓ resolveCheckPoint（Rule安定化 → 全Pending）
ENTER_PHASE：phase確定・表示更新 → PHASE_STARTED（異なるPhaseのときだけ）
  ↓
CHECK_POINT_AFTER_START：次stepをSTART_PHASE_PROCESSへ保存
  ↓ resolveCheckPoint（Rule安定化 → 全Pending）
START_PHASE_PROCESS：transitionをpop → 固有処理を一度だけ開始
```

`getNextPhase()`は遷移先の決定だけを担当する。STANDは既存Stage stand処理、DRAWは1枚ドローProcess、CLOCK / MAINは既存入力待ちProcessを開始する。STAND / DRAWは処理後も同じPhaseに留まる。CLIMAX / ATTACK / ENCORE / ENDの固有プレイは未実装のまま。同じPhaseへの明示的進入ではPhase Eventを再発行しない。

| 地点 | processStack（下 → 上） |
| --- | --- |
| 終了 / 開始AUTO提示 | PHASE_TRANSITION → PENDING_AUTO |
| AUTO解決 | PHASE_TRANSITION → AUTO_ABILITY（必要時さらに選択 / Rule child） |
| AUTO完了・残Pendingあり | PHASE_TRANSITION → PENDING_AUTO（Player優先を再評価） |
| Pending全処理後 | PHASE_TRANSITIONの保存済みstepへresume |
| 次Phase通常処理開始後 | 旧transitionなし。CLOCK / MAIN等の当該Processのみ |

Event dispatcherは誘発検出・Pending生成だけを行い、直接表示しない。使用 / 不使用いずれも残Pending全件処理後にresumeする。途中に増えたPendingも同じcollectionとTurn / Non-Turn優先で扱う。ACT / AUTOがstackに残る間は提示しない。Rule child → 親AUTO残処理 → AUTO COMPLETE → 残Pending → transitionの順を守る。

Check Point前のstep保存と、固有処理開始前のpopにより、Event再発行・Cost再実行・Phase Process再作成を防ぐ。進行中Process / Rule順序選択 / Mulligan / Game Over中は新規Phase進行を拒否する。Game Overではstackの継続を再開せず、既存の終了表示を維持する。Rendererは表示、Controllerは入力のみでresume判断を持たず、ProcessManager APIも変えない。

END → STANDの手番更新・Event snapshot順は従来どおりで、turn boundaryの整合は別Follow-upとする。今回のPhase境界接続完了はCLIMAX以降の実装完了を意味しない。
