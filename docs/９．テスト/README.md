# テストチェックシート運用

## 目的と正本

このREADMEを、チェックシートを作成・更新するときの運用上の正本とする。
チェックシートは、関数単位の単体テスト一覧ではなく、**ユーザーから確認できる操作・画面表示・ゲーム状態**を単位とした結合・画面レベルの確認観点を管理する。自動テストを置き換えるものではなく、画面を通した一連の動作を補完する。

対象はゲーム開始、フェイズ進行、カード選択・詳細表示・移動、Cost、ACT、AUTO、モーダル、Effect解決後の通常操作への復帰などとする。private methodや細かい関数単位は原則記載しない。DEVパネル自体は製品要件ではないため、DEVパネルの表示・操作も観点対象外とする（DEVパネルを準備に使い、製品機能を確認することは妨げない）。

## ひな形と実施結果の役割

- [チェックシートひな形](チェックシート_ひな形.md)は、全観点と確認手段を定義する。特定実施日の結果は記録しない。
- `実施結果/`のファイルは、特定の実施における結果を記録する。日付と対象が分かるファイル名にする。
- ひな形の「自動確認」にある`自動テストあり`は自動化済み・自動確認可能という**確認手段**を表し、今回テストを実行してpassした意味ではない。
- 実施結果の「自動確認」では、今回実行してpassした項目だけを`済`とする。実行しなかった項目は`割愛`、その確認方法が適用されない項目は`対象外`とする。
- ひな形の実機確認は、結果を持たない未選択状態`[ ] OK / [ ] NG / [ ] 割愛 / [ ] 対象外`とする。

## `#`の採番ルール

番号は`第1階層-第2階層-第3階層`（例：`1-1-1`）とし、チェックシート間で同じ観点を特定する安定IDとして扱う。

1. 第1階層はフェイズまたは大分類、第2階層はその中の分類、第3階層は個別の観点を表す。
2. 同一フェイズ・同一分類では第3階層だけを連番にする。
3. 既存観点の番号は原則変更しない。並べ替えや追加を理由に既存番号を詰め直さない。
4. 末尾への追加は、その分類の第3階層の最大値に1を加える。
5. 途中へ追加する場合も、表示位置にかかわらず同分類の未使用の次番号を割り当てる。見た目の連続性のために大量の既存番号を振り直さない。
6. 分類を追加するときは、そのフェイズ内の未使用の次の第2階層を割り当てる。廃止番号は再利用しない。
7. 番号はひな形と実施結果で一致させ、重複させない。

## 実施結果の作成手順（全量コピー方式）

新機能・画面・確認観点を追加した場合を含め、次の順序を必ず守る。

1. まずひな形へ観点を追加し、番号を付ける。
2. **更新後、その時点のひな形を全量コピー**して今回用の実施結果ファイルを作成する。
3. 今回確認した項目だけ、自動確認・実機確認の結果を記録する。
4. 確認しなかった項目も削除せず、該当欄を`割愛`にする。

抜粋方式は使用しない。実施結果には今回テストした観点とテストしなかった観点の両方を必ず残し、「ひな形には存在するが実施結果には存在しない」という状態を原則として作らない。毎回全項目を確認する必要はなく、変更に関連する観点を優先してよい。

## 記録値と実機確認

| 列 | ひな形 | 実施結果 |
| --- | --- | --- |
| 自動確認 | `自動テストあり` / `対象外`など、確認手段を記す | `済` / `割愛` / `対象外`（失敗時は備考に記録） |
| 実機確認 | `[ ] OK / [ ] NG / [ ] 割愛 / [ ] 対象外` | 4択のチェックボックスから原則1つだけ選択 |
| 備考 | 確認条件など | 条件、NG内容、結果の提供者などを簡潔に記す |

実機確認は、ユーザーがブラウザを実際に操作した結果である。結果確定後は、次のように原則1つだけを選択する。

- OK：`[x] OK / [ ] NG / [ ] 割愛 / [ ] 対象外`
- NG：`[ ] OK / [x] NG / [ ] 割愛 / [ ] 対象外`
- 割愛：`[ ] OK / [ ] NG / [x] 割愛 / [ ] 対象外`
- 対象外：`[ ] OK / [ ] NG / [ ] 割愛 / [x] 対象外`

**割愛**は、本来確認可能・確認対象になり得るが、今回の変更では確認しなかったものを指す。例えばAUTO関連だけを確認してMulliganを操作しなかった場合、Mulliganの実機確認は`割愛`である。

**対象外**は、その確認方法自体が観点に適用されないものを指す。例えばブラウザ操作で確認する意味がない内部的な観点である。「今回の変更と関係ない」という理由だけで`対象外`にせず、今回確認しなかっただけなら`割愛`にする。

自動テストのpassを実機確認OKとして扱わない。ユーザーから実機確認結果が提供された場合は実施結果へ転記してよいが、備考などでユーザーによる結果と分かるようにする。Codex自身がブラウザで確認していない実機結果を、テスト結果や実装から推測してOKにしてはならない。

NGが見つかった場合は、実機確認をNGにして備考へ内容を記録する。

## ブラウザ確認の補助操作

旧`test.md`の備忘を現行実装で確認して移管した。開発用画面では`main.dev.js`が次の変数を`window`へ公開しているため、Chromeの開発者ツールでConsoleを開いて利用できる。

```js
// 現在状態で再描画
renderer.render(gameState);

// テスト用card1を手札へ追加して再描画（状態整合性を保証しない直接操作）
gameState.players.self.hand.push(card1);
renderer.render(gameState);

// 次フェイズへ進める（入力待ちProcess中などは例外になる）
gameEngine.nextPhase();
```

コマンド自体は現在も公開変数/APIとして有効である。ただし手札への直接`push`はCardのzone/indexや元collectionを更新せず、Game Eventも発行しない古い簡易操作である。通常の結合確認ではDEVパネルまたはGameEngineの正規操作を優先し、このコマンドは表示調査だけに限定する。
